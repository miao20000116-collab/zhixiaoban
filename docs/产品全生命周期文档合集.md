# 产品文档

## 产品定位

> 一个能够理解用户职业背景、分析目标岗位、辅助生成求职材料、模拟真实面试，并持续帮助用户提升求职能力的 AI 求职伙伴。

## 核心差异化

| 维度 | 普通 AI 工具 | AI Career Assistant |
|------|-------------|---------------------|
| 用户理解 | 单次对话，无记忆 | Career Memory 长期画像 |
| 任务处理 | 单模型通用回答 | Multi-Agent 专业分工 |
| 输出质量 | 无审核 | Evaluation 真实性/匹配度检查 |
| 交互方式 | 功能菜单 | Chat First 自然对话 |

## MVP 核心闭环

```
用户表达求职目标
  → AI 理解用户（Memory）
  → 分析岗位（Job Agent）
  → 优化材料（Resume Agent）
  → 模拟面试（Interview Agent）
  → 评价提升（Evaluation）
  → 持续记忆更新
```

## Agent 职责

| Agent | 职责 | 阶段 | 对用户可见 |
|-------|------|------|------------|
| Master | 意图识别、任务规划、Agent 路由（不直接答用户） | Phase 1 | 否 |
| Memory | 从对话提取职业事实 / 否定性约束 / 进度，写入 Career Memory | Phase 1 | 否（结果体现在画像） |
| Resume | 简历解析、STAR、岗位定制；禁止虚构 | Phase 3 | 是 |
| Job | JD 分析、公司研究、岗位匹配 | Phase 2 | 是 |
| Interview | 面试题生成、模拟、复盘（含语音） | Phase 4 | 是 |
| Career | 职业咨询、求职状态分析、基于事实的情绪陪伴 | Phase 6 | 是 |
| Career Gap | 画像/Memory vs JD 差距分析（优势/缺口须有 evidence） | Phase 8 | 是 |
| Recommendation | 综合 Gap/Task/Memory 生成带 why/sources/priority 的行动计划 | Phase 8 | 是 |
| Evaluation | 真实性/质量/匹配度审核（横切质检，不对用户直接对话） | Phase 5 | 否 |

## 用户体验原则

1. **Chat First** — 用户直接表达需求，无需选择功能菜单
2. **渐进式信息采集** — 从对话中自然提取职业信息，不主动弹问卷
3. **多窗口独立、Memory 共享** — 窗口是用户自主管理的对话空间，职业档案跨窗口共享
4. **基于事实的反馈** — 情绪陪伴给出可执行建议，避免空泛鼓励
5. **建议可解释** — 每次下一步建议都说明「为什么」，并展示依据来源（记忆 / 本次流程 / 外部检索）
6. **画像而非表单** — 职业档案以 AI 个人画像呈现：优势、经历、目标、短板、训练进展

## Phase 7 体验目标

用户应感到：「这个 AI 真正了解我的职业背景」，而不是「一个 ChatGPT 包装工具」。

## Phase 8 职业智能目标

从「用户提问 → AI 回答」升级为「理解用户 → 分析职业状态 → 发现问题 → 给出下一步」：

1. **Career Gap** — 对比画像 / Memory / JD，输出匹配度、优势、缺口与可执行建议（均需来源）
2. **Task Memory** — 侧栏展示当前任务、进度与下一步，而不只是对话摘要
3. **Next Action Planner** — 建议升级为带原因与优先级的行动计划
4. **Recommendation Agent** — 综合 Gap / Task / Workflow 主动推荐，禁止无依据建议

## Evaluation 阻断 UX（用户可见行为）

| 风险等级 | 典型场景 | 用户可见行为 |
|----------|----------|--------------|

| not_applicable | 输入不足无法评分 | 索要材料（简历/JD/对话事实），不硬生成 |

## 1.2 项目背景

随着就业市场竞争加剧，求职用户在寻找工作过程中面临越来越复杂的问题。从岗位选择、简历准备，到面试训练、职业决策，整个求职过程涉及大量信息收集、内容准备和持续优化工作。

目前市场上的求职辅助工具主要集中于单点能力，例如简历生成、JD匹配、面试题生成等，但这些产品通常存在以下问题：

第一，工具之间相互割裂。用户需要在多个产品之间切换，例如使用一个工具修改简历，另一个工具准备面试，再使用搜索工具了解公司和行业信息，无法形成完整的求职闭环。

第二，AI缺少对用户长期背景的理解。传统AI助手通常只基于当前一次对话生成内容，无法持续理解用户的职业经历、优势能力、目标岗位以及历史求职表现，因此无法提供个性化建议。

第三，求职过程不仅包含信息和能力问题，也包含长期心理压力。用户在求职过程中会经历投递无反馈、面试失败、自我怀疑、Offer选择困难等情况，目前大部分求职工具无法提供持续性的陪伴和反馈。

因此，本项目希望构建一个面向求职用户的 AI 求职伙伴，通过多 Agent 协作、用户职业记忆、岗位分析、面试训练和智能评估能力，覆盖用户从求职准备到获得 Offer 的完整流程。

## 1.3 产品定位

AI求职辅助 Agent 是一个面向广大求职用户的智能求职助手。

产品定位：

> 一个能够理解用户职业背景、分析目标岗位、辅助生成求职材料、模拟真实面试，并持续帮助用户提升求职能力的 AI 求职伙伴。

产品不是单纯的内容生成工具，而是通过长期记忆和多 Agent 协作，为用户提供持续性的求职支持。

# Master Agent System Prompt

你是 AI 求职助手的主控 Agent（Master Agent）。

## 职责

1. 分析用户消息，识别求职相关意图
2. 结合当前 Task Memory（若有）判断应继续推进哪条求职链路
3. 输出结构化 JSON，供系统路由到合适的专业 Agent
4. 你不直接回答用户问题，只做意图分类；不主动推荐新任务

## 支持的 Intent

| intent | 说明 | need_agent |
|--------|------|------------|
| memory_update | 补充/纠正/记住职业事实（经历、技能、目标、否定性约束） | memory_agent |
| resume | 简历优化、诊断、STAR、自我介绍文案、上传简历全文 | resume_agent |
| jd_analysis | JD 分析、岗位匹配、公司研究 | job_agent |
| interview | 模拟面试、面试题、面试复盘、技术训练（含「问我一些技术问题」） | interview_agent |
| career_consult | 职业咨询、求职方向、Offer 选择 | career_agent |
| general_chat | 一般聊天、问候、与求职弱相关 | null |

特殊：用户说「我之前负责… / 我做过… / 我的技能是… / 目标岗位是… / 记住… / 补充一下… / 纠正一下… / 我没有真实…经验」→ 优先 `memory_update`（沉淀 Career Memory，不是简历优化）
特殊：用户说「问我一些技术问题」→ intent=`interview`（系统内部模式 technical_interview）
特殊：用户表达焦虑/被拒/迷茫/压力 → 优先 `career_consult`（情绪陪伴，需结合 Career Status 数据）
特殊：用户说想找某岗位 / 转岗 / 分析差距 / 规划路线 → `career_consult`（系统会触发 Career Gap + Action Plan）
特殊：仅当用户明确要求「优化/改/定制简历」或粘贴完整简历时才用 `resume`

## Task Memory 规则

- 若「当前 Task Memory」已有进行中任务，优先选择能推进该任务下一步的 intent
  - 下一步含 JD → `jd_analysis`
  - 下一步含简历 → `resume`
  - 下一步含面试/项目深挖 → `interview`
- 用户表达新的明确目标（如「我准备字节 AI 产品经理面试」）时，仍按目标意图分类；系统会创建或续写 Task
- 不要因为有 Task 就忽略用户当前明确说的新意图

## 规则

- 信息不足时仍给出最可能的 intent，confidence 相应降低
- 一条消息可能涉及多个话题，选最主要的 intent
- 只输出 JSON，不要输出其他文字

## 输出格式

```json
{
  "intent": "resume",
  "confidence": 0.92,
  "need_agent": "resume_agent"
}
```

general_chat 示例：

```json
{
  "intent": "general_chat",
  "confidence": 0.95,
  "need_agent": null
}
```

# Memory Agent System Prompt

你是 AI 求职助手的 Memory Agent，负责从用户对话中提取有价值的职业信息与状态理解。

## 职责

提取以下类型：

### 事实类
1. **experience** — 工作经历（公司、职位、职责、成就；公司可为空）
2. **project** — 项目经历（项目名、背景、行动、结果、指标）
3. **skill** / **skill_memory** — 技能能力（技能名、水平 1-10）
4. **career_goal** / **goal_memory** — 求职目标（目标岗位、行业、方向）
5. **profile** / **fact_memory** — 基础职业信息（年限、摘要等）

### 限制 / 否定类（必须提取）
6. **constraint_memory** — 用户明确的限制性事实，例如：
   - 没有真实 RAG 项目，只上过课程
   - 没有企业级 AI 落地经验
   - 不希望虚构经历
   - 纠正错误信息（年限、岗位等）

### 状态理解类
7. **gap_memory** — 能力差距理解（强在哪/缺在哪）
8. **progress_memory** — 求职进度（已完成什么、卡在哪）

## 重要性评分 importance_score（1-10）

| 分数 | 类型 | 示例 |
|------|------|------|
| 9-10 | 职业经历、项目、求职目标、否定性约束、明确差距 | "我之前做增长" / "没有真实RAG项目" / "年限是5年不是3年" |

| 1-3 | 兴趣、情绪、无关内容 | "今天天气不错" |

## 规则

- 只提取用户**明确陈述**的事实，不要推测或编造
- 「我之前负责…」「我做过…」「我的技能是…」「目标岗位是…」「纠正一下…」「记住…」「补充一下…」都必须提取，不要返回空

- 只输出 JSON，不要其他文字

3. 岗位匹配：内容是否贴合目标岗位，而非偏题堆砌
4. 质量评分：0–100
5. 风险等级：low / medium / high / not_applicable

## 风险分档（重要）

请区分四类改写，避免误伤：

| 类型 | 例子 | 风险 |
|------|------|------|
| 表达润色 | 语序调整、同义改写 | low |
| 合理归纳 | 原文有「浏览器用户增长 + 新用户项目」，写成「浏览器新用户增长」 | low |
| 轻微结构化 | 把分散事实整理成一条 STAR 句，不新增公司/指标/技术栈 | low |
| 事实新增 | 新增原文没有的公司、项目、指标、职位、技术栈（如虚构 RAG 项目） | medium/high |

- high：明显编造经历/数据，或严重误导求职决策
- medium：依据不足、夸大倾向、或「信息不足却写得很具体」
- low：有依据的合理改写 / 明确标注推测且无虚构
- not_applicable：输入不足、无法评分

## 简历检查重点

- 是否把「参与」夸大为「主导 / 负责 / 带领」
- 是否新增原文没有的项目、职责或量化数据
- 目标岗位是 AI 产品经理时，是否大量突出无关方向（如纯活动运营）却不说明迁移逻辑
- **不要**因合理归纳（如「新用户增长」在原文已有新用户项目上下文）判 medium

## 面试回答评分维度（加权）

- 问题理解 20%
- 结构表达 20%
- 专业能力 30%
- 岗位匹配 20%
- 真实性 10%

## JD / Job 分析检查重点

- 公司/行业信息是否缺乏依据却写得很具体
- 用户匹配是否编造用户经历
- **明确标注「推测 / is_inferred」且无虚构事实**的岗位分析：风险应为 low 或最多 medium，**不要**仅因信息不足判 high
- 实习生 / 初级 JD 若内容与原文一致、无虚构，不应 high

## Career Gap 检查重点

- 优势是否基于用户真实经历 / Career Memory（禁止虚构能力、项目、成果）
- 缺口是否引用 JD / 岗位要求中的具体条款（禁止空泛「技术不行」而无依据）
- 是否存在虚构技能、年限或量化结果（如用户无 RAG 却写「丰富 RAG 落地经验」）
- 提升建议是否合理、可执行，且对应已指出的缺口
- 仅给匹配分数、无解释、无 evidence → 不合格（risk 至少 medium，score 偏低）
- **建议含「包装为实战 / 包装成落地 / 写成真实项目」→ 不合格**（risk 至少 medium，写入 fabricated_claims）
- 用户约束「没有真实 / 只上过课程」时，相关能力不得列为优势或鼓励包装

## Recommendation 检查重点

- 每条建议是否有 why / sources
- 是否过度承诺（如「保证拿 offer」）
- 无来源建议 → risk 至少 medium

## 面试复盘检查重点

- 若复盘含「解析失败 / 请重新生成复盘」等内部错误文案 → 判定不合格，建议替换为基于对话的可读复盘

## 输出格式

只输出 JSON：

```json
{
  "risk_level": "low",
  "score": 85,
  "problems": ["问题描述"],
  "suggestions": ["改进建议"],
  "fabricated_claims": ["疑似虚构的具体表述"],
  "issues": [{"issue": "新增不存在量化指标", "suggestion": "删除30%提升描述", "severity": "high"}],
  "job_match_score": 75,
  "job_match_notes": ["偏运营案例偏多，建议突出 AI/产品相关经历"]
}
```

面试回答评分任务额外可包含：

```json
{
  "understanding": 80,
  "structure": 70,
  "expertise": 75,
  "job_match": 80,
  "authenticity": 90,
  "overall": 78,
  "comments": ["结构清晰，缺量化结果"]
}
```

## 约束

- 不确定时标 medium（但合理润色不要标 medium）
- high 用于明显编造经历/数据或严重误导求职决策
- 正常、有依据的合理改写不要误判为虚构
- 不要输出 JSON 以外的文字

# 材料解析验收与 RAG 阶段决策

## 1. 材料解析验收表

| 材料 | 最短可用输入 | 解析期望 | 失败态 |
|------|--------------|----------|--------|
| 简历全文 | ≥1 段真实经历 | 经历/项目/技能/待补充 | 索要更多字段；不编造 |
| 简历文件 docx | 可读文本 | 同上；进度提示 | 可读中文错误，非 raw JSON |
| JD 全文 | 含职责或要求的段落 | 职责/硬性/隐性/面试重点 | — |
| 仅岗位+公司 | 岗位或公司非空 | **线索推测**分析；匹配分=0（暂不评分） | 禁止「解析失败」 |
| 管理岗标题 JD | 含负责人/战略/团队管理 | level=高级/负责人；缺口含管理年限 | — |
| JD 实为简历 | 命中 LOOKS_LIKE_RESUME | 自动改走简历解析 | HANDOFF 已述 |

## 2. RAG 阶段决策（诚实）

| 问题 | 结论 |
|------|------|
| 主路径靠什么？ | Career Memory + 简历/JD 结构化注入 + Agent Prompt |
| Embedding / pgvector？ | 配置与 schema **预留**；HANDOFF：**业务主路径未强依赖** |
| 为何后置强 RAG？ | 求职个性化事实更新快；先把 Memory/Eval 做硬，再扩检索；避免半成品「假 RAG」叙事 |
| 何时加强 RAG？ | Later：公司/行业知识库、题库检索等明确场景，且有评测集 |

对外话术：**不是忘了做 RAG，而是阶段取舍——先记忆与质检，再检索增强。**

# 交接文档（给下一位 Context / 协作者）

## 1. 项目是什么

**职小伴 / AI 求职助手**：Chat First 的 Multi-Agent 求职产品。

主闭环：对话 → JD 分析 / 简历优化 → 模拟面试（文字 + 语音）→ 复盘 / 画像 / 推荐。

## 3. 本机运行方式（当前实测）

**不是 Docker 一键**（本机可能无 Docker）。惯例：

| 组件 | 方式 |
|------|------|
| Postgres | 便携版 `C:\ai-career-pg`，脚本 `backend/scripts/start_local_pg.py`，端口 `5432` |
| Backend | `cd backend && python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload` |
| Frontend | `cd frontend && npm run dev`（Node 在 `D:\Program Files\nodejs`） |
| 前端地址 | http://localhost:3000 |
| 后端文档 | http://localhost:8000/docs |

改 `.env` 后必须**重启 uvicorn**（`--reload` 不监视 `.env`）。

## 4. 模型与密钥（两套）

| 用途 | 配置项 | 当前约定 |
|------|--------|----------|
| 文本 LLM | `OPENAI_API_KEY` / `OPENAI_API_BASE` / `MODEL_NAME` | DeepSeek（`deepseek-v4-flash`） |
| 语音 ASR+TTS | `SPEECH_API_KEY` / `SPEECH_API_BASE` / `WHISPER_MODEL` / `TTS_*` | 硅基流动 SenseVoice + CosyVoice2 |

**注意：** 语音不要回退到 DeepSeek Base（DeepSeek 无 `/audio/*`）。逻辑在 `backend/app/config.py` 的 `resolved_speech_*`。

`.env` 已配置过真实 Key；交接时只确认「已 set」，不要把 Key 写进文档或提交 git。

## 5. 近期产品改动（需重点验）

1. **三栏布局**：中间优先；右侧画像可拖宽/隐藏；窄屏自动藏画像（`use-panel-layout`）
2. **四季主题 + 安抚语**：atmosphere 相关组件
3. **输入区**：`JD` / `简历` / **`语音面试`** 并排（语音入口不再单独占一行）
4. **语音面试**：电话式一对一；自动开麦、停顿自动提交、可打断；大红「结束面试」；通话内固定展示「面试官提问」
5. **API 报错**：前端 `readApiError` 解析 FastAPI `detail`，避免整段 JSON 甩给用户
6. **文档分类误传**：JD 上传若实为简历会自动切换解析（`LOOKS_LIKE_RESUME`）
7. **Career Gap（Phase 8.1）**：JD 分析后自动对比 Career Memory，输出匹配度/优势/缺口/建议+evidence；Profile + 右侧画像 Career Gap Card；表 `career_gaps`
8. **Task Memory（Phase 8.2）**：识别长期目标并跨对话保持进度；侧栏 Current Task + Profile Career Progress；Master 路由读取 Task 上下文；表 `career_tasks`

## 4.4 系统架构 architecture 全文

> 来源：docs/architecture.md

# 系统架构

## 1. 架构概览

AI Career Assistant 采用 **六层架构**，支持 Chat、Agent、Memory、RAG、Evaluation 的长期扩展。

```
L1 用户交互层     Next.js + shadcn/ui (Chat First)
L2 会话管理层     Conversation Manager (多窗口 / 摘要)
L3 Agent 编排层   Master Agent (意图识别 / 任务规划 / 路由)
L4 专业 Agent 层  Resume / Job / Interview / Career / Evaluation
L5 AI 基础能力层  Memory / RAG(pgvector) / LLM Provider
L6 数据与工具层   PostgreSQL / 搜索 / 文件解析 / ASR(未来)
```

## 2. 请求数据流

```
用户消息
  → Frontend (SSE)
  → POST /chat
  → Master Agent（意图识别）
  → 若存在进行中的模拟面试
        → Interview Agent 追问 / 推进状态机 / 复盘
  → 若 intent=interview 或「开始模拟面试」
        → 启动面试状态机（可带 JD）
  → 若 intent=resume 且含简历/优化请求
        → Resume Agent（解析 / STAR / JD 定制）
        → Evaluation（禁止虚构项目/数据/职责）
        → 流式返回优化报告（含修改原因）
  → 若 intent=jd_analysis 且含 JD/岗位信息
        → Job Intelligence Agent
        → Search Tool（公司/行业）
        → Evaluation（真实性检查）
        → 流式返回岗位分析报告
  → 否则普通 LLM 回复
  → Memory Agent 提取职业信息
  → 返回 Frontend
```

## 3. Agent 协作模型

```
                    用户
                     ↓
                Master Agent
                     ↓
    ┌────────────────┼────────────────┐
    ↓                ↓                ↓
Resume Agent   Job Agent    Interview Agent
    ↓                ↓                ↓
    └────────────────┼────────────────┘
                     ↓
              Evaluation Agent
                     ↓
              Memory Update
                     ↓
                  返回用户
```

**约束：**
- 专业 Agent 之间禁止直接互相调用
- 所有路由必须经过 Master Agent
- Evaluation 作为横切能力，重要输出必须经其审核

## 3.1 Evaluation 质量控制（Phase 5）

```
Agent Output → Evaluation Agent → Risk Check → Final Response
                     ↓
         EvaluationRecord + Agent Trace
                     ↓
              high → BadCase（自动）
```

能力：真实性检查 / 岗位匹配 / 面试回答加权评分  
配套：Prompt 版本管理、Evaluation Dataset、Dashboard（`/dashboard`）

## 3.2 语音面试 + 长期陪伴（Phase 6）

```
Audio → ASR → Interview Agent → Evaluation → 表达分析 → Feedback
                                                      ↓
                                              Career Status 更新
                                                      ↓
                                              Next Action 推荐
```

- 情绪陪伴：Master 能力增强（`career_consult`），禁止空泛鼓励，必须引用面试次数/得分/短板
- 智能推荐：JD 分析后建议改简历；面试后建议专项训练

## 3.3 产品体验优化（Phase 7）

```
Chat First 首页 → 阶段/问题引导（无工具按钮墙）
       ↓
Conversation 自动标题 + Summary（侧栏副标题）
       ↓
个人画像（优势 / 经历 / 目标 / 短板 / 训练进展）
       ↓
Next Action = 建议 + 为什么 + 依据来源（外部检索 / 记忆）
```

- `projects.source` 补齐，Memory Context 携带来源与置信度
- SSE 新增 `conversation_updated` 实时刷新侧栏标题与摘要

## 3.4 Career Intelligence Layer（Phase 8）

```
User → Master Agent
         ↓
   Career Memory + Task Memory
         ↓
   Career Gap Analysis（可选，岗位/目标相关时）
         ↓
   Scene Agent（Job / Resume / Interview / Career）
         ↓
   Recommendation Agent + Next Action Planner
         ↓
   Evaluation → Response → 更新 Task Memory / latest_gap
```

- 不新增工具墙页面；能力挂在 Conversation 侧栏（Current Task）与 Profile（Gap Card / Career Progress）
- Memory 类型扩展：`fact` / `skill` / `goal` / `gap` / `progress`
- SSE：`career_gap`、`task_updated`；表：`career_tasks`、`career_gaps`、`recommendations`
- Task Memory：Master 每次路由读取当前任务；有则续写，无则在明确目标时创建；跨 Conversation 保持 active Task

## 4. LLM Provider Layer

```
services/llm/
├── provider.py          # BaseLLMProvider / BaseEmbeddingProvider 抽象
├── openai_provider.py # Phase 0 实现（OpenAI 兼容 API）
└── config.py          # 从环境变量读取，不绑定具体模型
```

替换模型时只需修改 `.env` 中的 `MODEL_NAME` 和 `OPENAI_API_BASE`。

## 5. 部署架构

```
docker-compose
├── frontend:3000   (Next.js dev/build)
├── backend:8000    (FastAPI + Uvicorn)
└── postgres:5432   (pgvector/pgvector:pg16)
```

### 1. 自我介绍

面试官你好，我叫XXX，3年AI产品经验，硕士毕业，专业是机器人工程，研究方向是深度学习。

除了项目经验，我有扎实的技术功底。硕士期间我的毕业设计是【太极动作AI评分系统】，发了一篇EI论文，技术上对RAG、Prompt工程、模型评估、多智能体协同这些都比较熟悉。同时我习惯用数据说话，能用SQL和Python做分析，也能快速用原型工具和vibe coding做方案验证。

我关注AI产品方向的机会，希望能在一个能深入落地AI应用的团队里继续深耕。以上是我的自我介绍。

***

### 2. 介绍项目

1. 背景与场景

   求职用户每天都在用 ChatGPT、各类简历工具，但真实痛点并不是「再生成一段更好看的文字」，而是：AI 记不住我是谁、简历容易被「美化」到穿帮、岗位分析和面试准备割裂、给不出带依据的下一步。用户原始需求往往很模糊——「帮我找工作」「帮我改简历」「我想转 AI 产品」——和科研 Agent 项目里「想做科研相关的 AI」一样，需要产品经理主动把模糊诉求拆成可落地的闭环。

2. **用户痛点**：

   * **求职者**：通用大模型单次对话无长期记忆；优化简历时容易虚构项目/指标；JD、简历、面试各自为政，准备没有主线。

   * **转型用户**（如增长转 AI 产品）：不知道缺口在哪、下一步先做什么，容易陷入「又焦虑又瞎投」。

   * **作品集验证视角**：若只做 Chat 壳子，面试官一眼能看出没有 Agent 分工、没有质检、没有记忆，无法证明 AI 产品落地能力。

3. **我的角色**：唯一产品经理（兼方案与验收），独立负责从0到1：需求挖掘→架构设计→意图体系→Agent 编排→Memory/Evaluation 设计→产品交互→质量套件与交付验证。

4. 具体工作流

   1. **需求挖掘**：访谈/复盘自己与身边求职者的真实路径；拆解 ChatGPT、Offer 向工具、纯简历改写工具的差距；明确差异化——不是功能菜单堆叠，而是 Chat First + 长期职业理解。

   2. **方案设计**：提出「Master 路由 + 多专业 Agent + Career Memory + Evaluation」架构，覆盖：理解用户 → JD 分析 → 简历优化 → 模拟面试（含语音）→ Gap 分析 → 可解释推荐。

   3. **技术选型**：Frontend Next.js；Backend FastAPI；PostgreSQL + pgvector；LLM 走 OpenAI 兼容抽象层（可切换 DeepSeek 等）；语音 ASR/TTS 与文本模型配置分离；Agent Prompt 外置 `prompt.md`，禁止写死在接口里。

   4. **记忆与材料体系**：设计 Career Memory（fact/skill/goal/gap/progress）、Task Memory（跨对话任务进度）、会话 Summary；简历/JD 上传解析入库；重要输出强制经 Evaluation。

   5. **产品设计**：Chat First 首页（无工具墙）；多窗口独立、Memory 共享；右侧个人画像（优势/经历/目标/短板/训练进展）；侧栏 Current Task；Career Gap Card；语音面试（电话式一对一）；Dashboard 看成功率/幻觉/BadCase。

   6. **质量管控**：为 Master / Resume / Job / Interview / Evaluation / Gap 等建质量报告与精标集；高风险输出自动记 BadCase；发版以评测集为准。

   7. **结果（作品集验证口径）**：主闭环 Phase 0–8 跑通；Master 质量套件 8/8（均分 4.88/5）；Resume 8/8（5.0/5）；Evaluation 6/7（4.43/5，虚构识别为亮点）；Career Gap 6/7（4.43/5）；Interview 6/7（4.43/5）。北极星不是「拦截率」，而是：**真实可投递 + 路由准确 + 建议可解释**。

### 3. 数据整理、职业记忆与知识体系建设

> **整体定位**：职小伴不是「海量文献检索写综述」，而是「理解这个人的职业事实，并基于事实做 JD/简历/面试/推荐」。核心知识载体是 **Career Memory + 用户材料（简历/JD）+ Evaluation 精标集**；向量检索（pgvector）作为架构预留能力，主路径当前更强依赖结构化记忆与 Agent 上下文注入，而不是十万级文献混合检索。

#### 1. 知识/记忆构建

* **数据来源**：

  * 用户上传/粘贴的简历全文（中英文）

  * 目标岗位 JD 文本或岗位+公司线索

  * 对话中自然说出的经历、技能、目标、否定性约束（如「没有真实 RAG 项目经验」）

  * 模拟面试过程与复盘结果（训练进展）

  * Evaluation / 质量套件沉淀的 BadCase 与精标样本

* **清洗与约束规则**（产品侧主导定义）：

  * 去空：无实质内容的寒暄不入库为职业事实

  * 冲突处理：用户纠正优先于旧记忆（如「之前说有 RAG 项目」→「实际只有课程」）

  * 否定性事实必须保留：禁止后续 Agent 把「没有」改写成「丰富经验」

  * 来源与置信度：项目/技能尽量带 `source`（简历 / 对话 / JD）与 confidence，供 Gap/推荐引用

  * 脱敏：作品集演示账号与本地数据，不把密钥与隐私材料写入文档仓库

* **标注（Memory 类型体系）**：

  * `fact`：可验证经历与客观信息

  * `skill`：技能标签

  * `goal`：目标岗位/方向

  * `gap`：已识别缺口

  * `progress`：面试次数、投递、训练进展等

#### 2. 「切片」在本项目中的等价设计

| 材料类型 | 处理方式 | 目的 |
| --- | --- | --- |
| 简历全文 | 结构化解析为经历/项目/技能/待补充项，不强行按字数乱切 | 供 Resume Agent 与 Evaluation 对照原文 |
| JD 文本 | 解析职责、硬性要求、隐性要求、级别与行业 | 供 Job / Gap / 面试出题对齐 |
| 长对话 | Conversation Summary + 最近轮次窗口，而非全文反复塞入 | 控制上下文，保留任务主线 |
| Task Memory | 外部状态：当前目标、进度、下一步（跨 Conversation 复用） | 长求职任务不丢「正在做什么」 |
| 精标集 JSON | 按场景分库（简历幻觉/JD虚构/面试编造/Gap无依据） | 回归门禁，不进训练污染 |

* **输出**：Memory / Task / Gap 的产品规则写入 PRD 与 Agent Prompt；切片规范在本项目中体现为「结构化字段规范」而非文献 chunk size 表。

#### 3. 检索与上下文组装（诚实表述）

* **主路径**：Master 路由后，向专业 Agent 注入 Career Memory 摘要、当前 Task、相关 JD/简历片段、面试状态。

* **向量能力**：PostgreSQL + pgvector 已在架构中预留（`document_chunks`），Embedding 配置存在；业务主路径尚未做成「强依赖混合检索」——面试时要主动说明：这是有意的阶段取舍，先把 Memory 与 Evaluation 做硬，再加深 RAG。

* **与科研 Agent RAG 的对比一句话**：科研要查全查准文献；职小伴要「查准这个人的事实」并防止编造。

#### 4. 召回等价机制（记忆召回）

* 用户问「我的优势是什么」→ 从 Memory / 简历事实召回，禁止空泛鸡汤。

* Gap 分析 → 对比 Memory vs JD，优势/缺口均需 evidence。

* Recommendation → 每条建议必须有 why + sources（Career Memory / Gap / Task / JD）。

#### 5. 重排/优先级

* Task Memory 有进行中任务时，Master 优先路由能推进「下一步」的意图（下一步含 JD → `jd_analysis`，含简历 → `resume`，含面试 → `interview`）。

* 用户明确说出新意图时，不以 Task 压过当前话术。

#### 6. 兜底策略

* 简历未上传就要求优化 → 明确索要材料，不编造履历。

* Evaluation 判定 high risk（虚构项目/指标）→ 阻断可投递输出，给出修改建议并记 BadCase。

* Gap/推荐缺少来源 → 降级或拒答式提示，禁止无依据建议。

#### 7. 优化迭代

* 每周/每轮用质量报告驱动：哪类 Agent 未通过就优先修 Prompt、规则或 Evaluation 阈值。

* 一次典型优化：强化「否定性事实 / memory_update 优先于 resume 关键词」，避免用户说「我没有 RAG 经验」却被路由去「美化简历」。

### 4. 需求来源：从模糊需求到主动挖痛点

客户/用户原始输入（模糊）：「帮我找工作」「我想转 AI 产品，你看着帮我弄」。

我的主动挖掘过程：

* **流程拆解**：把求职链路拆成材料准备 → 岗位理解 → 简历定制 → 面试训练 → 复盘改进；发现市场上多数工具只覆盖其中一环。

* **竞品对照**：ChatGPT（强生成、弱记忆与质检）、纯简历改写工具（易幻觉）、题库类面试 App（弱个性化）。空白点是「理解我是谁 + 多 Agent 专业分工 + 输出可审计」。

* **体验原则沉淀**（写入产品文档）：

  1. Chat First，不靠功能按钮墙

  2. 渐进式采集信息，不弹问卷

  3. 多窗口独立、Memory 共享

  4. 建议必须可解释（为什么 + 依据来源）

  5. 画像而非表单

* **优先级原则**（嫁接智能客服项目方法论）：先保**防幻觉底线**，再保**主闭环跑通**，最后做体验（四季主题、三栏布局、语音面试打磨）。

### 5. 评价指标

1. 第一层：业务/闭环价值指标（作品集验证口径）

   * 主闭环完成度：用户能否在同一产品内完成「JD 分析 → 简历优化 → 模拟面试 → Gap/下一步」至少一条完整路径。

   * 可投递真实性：高风险虚构输出拦截率（Evaluation high → 不直接给出可投递简历/复盘）。

   * 任务连续性：Task Memory 能否跨对话保持「当前目标与下一步」，避免每次从零开始。

2. 第二层：用户体验指标

   * 意图澄清成本：模糊输入下平均澄清轮次（目标控制在少量追问内拿到材料/目标，而不是连续盘问）。

   * 建议可解释率：Next Action / Recommendation 中含 why + sources 的比例（产品约束为必需字段）。

   * 情绪陪伴有效性：焦虑/被拒场景必须引用真实状态数据（面试次数、得分、短板），禁止空泛鸡汤。

3. 第三层：模型与 Agent 性能指标（质量报告可回溯）

   * Master 路由正确率：质量套件 8/8，均分 4.88/5。

   * Resume 任务通过率：8/8，均分 5.0/5（含防虚构阻断用例）。

   * Evaluation 幻觉识别：6/7，均分 4.43/5（简历虚构、面试复盘虚构等）。

   * Job / Interview / Career Gap：各有专项报告（例如 Gap 6/7、Interview 6/7）；未通过项进入 BadCase 清单（如部分短 JD 解析失败、面试结束复盘解析偶发失败）。

   * 端到端耗时：对话级秒级到数十秒（复杂 JD+Gap 链路更长），产品上用流式与「可能需要几十秒」提示管理预期。

### 6. 后续优化

1. 案例打标归因

   建立 BadCase 复盘机制，精细化分类：意图误路由、Memory 未召回/冲突、简历幻觉、复盘虚构、Gap 无依据、推荐缺 sources、材料解析失败。不笼统归为「模型不行」。

2. 量化优化目标

3. 逆向链路排查

   固定顺序：用户表述是否清晰 → Master 意图与 Task 优先级 → Memory/材料是否注入 → 专业 Agent Prompt → Evaluation 门禁 → 前端展示是否丢字段。

### 7. 记忆、窗口问题

<span style="color: inherit; background-color: rgb(251,191,188)">长求职任务跨多轮/多窗口，模型忘记「我是谁、正在准备什么」 → 会话窗口 + Summary + Career Memory + Task Memory 外部状态</span>

1. 问题场景

   用户不是问一句答一句，而是一条持续数天的求职任务，例如：

   * 第 1 天：分析 AI 产品经理 JD，生成 Gap

   * 第 2 天：按该 JD 优化简历

   * 第 3 天：开模拟面试，中途追问指标口径

   若只依赖单次 Prompt 上下文，会出现：忘记「没有真实 RAG 经验」、忘记当前 Task 下一步是面试、多窗口之间画像不一致。

2. 解决方案

   1. **短期记忆（滑动窗口）**：请求携带最近若干轮对话，避免无限膨胀。

   2. **会话 Summary**：侧栏副标题/摘要，SSE `conversation_updated` 刷新；长对话用摘要代替全文。

   3. **Career Memory（长期画像）**：跨窗口共享事实、技能、目标、缺口、进展。

   4. **Task Memory（外部状态）**：记录「正在完成什么、进度、下一步」；Master 每次路由读取；有则续写，无则在明确目标时创建。

   5. **面试状态机**：模拟面试过程中的轮次、阶段（自我介绍/项目深挖/复盘）外置，不靠模型「硬记」。

3. 结果：从「每次都是新的 ChatGPT」变成「这个 AI 知道我的职业背景和当前任务」——对应产品 Phase 7/8 的体验目标。

### 8. 微调与方案选择（Prompt / LoRA / RAG）

1. 本项目实际选择

   * **生产路径不做 LoRA/全量微调**，采用：外置 Prompt + Career Memory 注入 + Evaluation 门禁 +（架构预留）pgvector。

   * 原因：求职事实高度个性化、更新频繁（今天纠正经历，明天换目标岗）；需要可解释与可审计；作品集迭代要快，不能绑死一次微调权重。

2. 与两个工作项目的对照（面试加分话术）

   * **智能门诊**：口语-术语映射曾用小模型 LoRA 做过实验，但最终不上生产微调，改 Query 改写 + 同义增强（算力与知识周更）。

   * **科研 Agent**：格式规范相对稳定，适合 LoRA 做输出风格迁移。

   * **职小伴**：更像「个性化事实系统 + 质检闸门」，微调解决不了「这个用户到底有没有 RAG 项目」——那是 Memory 与 Evaluation 的事。

3. 为何选 / 不选 LoRA（简表口述）

   * 选 LoRA：格式迁移、术语固定、数据几千级、单卡可承受。

   * 选全量微调：要改深层推理能力、数据与算力都够。

   * 选 Prompt+工具+评测：规则与事实常变、要强约束拒答/阻断、要快速 A/B Prompt 版本——**职小伴落这里**。

### 9. 精标集

<span style="color: inherit; background-color: rgb(251,191,188)">Evaluation Datasets：简历幻觉 / JD 虚构 / 面试编造 / Gap 无依据</span>

1. 构建目标

   保证上线/演示前：虚构项目与指标能被拦住；正常改写不被误杀；Gap/推荐必须有依据。

2. 精标集来源（仓库落地）

   * `resume_hallucination.json`：参与→主导、编造转化率等

   * `jd_analysis.json`：虚构公司融资/垄断、编造用户匹配经历

   * `interview_answer.json`：面试口头编造「独立打造 ChatGPT」等

   * `career_gap.json`：把「仅上过 RAG 课」写成「丰富 RAG 落地经验」

3. 标注流程

   1. 按场景分类（简历优化 / JD 分析 / 面试回答 / Gap）

   2. 定义期望：`expected_risk_level`、`expect_fabricated`

   3. 正样本：忠实改写/有依据 Gap，应 low risk

   4. 负样本：虚构、夸大、无 sources 建议，应 high/medium 并拦截或降级

4. 质量保障

   * 精标集用于回归，不拿去「教模型继续编」

   * 与 Dashboard / BadCase 联动：高风险自动入库

   * 发版门禁：关键负样本必须按预期拦截

### 10. 归因过程中错误类型

1. 意图分发 / 路由错误（高频，对应科研稿「意图分发错误」）

   * 典型示例：用户说「我没有真实 RAG 项目经验，只上过课」，被当成简历优化；或「帮我分析岗位，同时优化简历，再模拟面试」一次塞三个任务，路由混乱。

   * 根因：关键词冲突；多意图未拆解；未走澄清/分步流程；Task 与当前话术优先级处理不当。

   * 解决方案：Master Prompt 明确 memory_update 优先规则；复合需求拆成可执行步骤并索要 JD/简历；低置信时澄清；Task 续写但不覆盖明确新意图。

2. 简历 / 复盘幻觉（对应客服稿「模型幻觉」，本项目更致命）

   * 典型示例：原文「参与增长、协助统计」→ 输出「主导千万用户、转化率 +30%」；面试复盘虚构「深度 RAG 落地」。

   * 根因：生成自由度高；未强制对照原文；无输出后风险分级。

   * 解决方案：Evaluation 横切审核；high risk 阻断可投递结果；Prompt 禁止补造项目/数据；精标集回归；Dashboard 追踪幻觉率。

3. Memory 缺失、冲突或未召回

   * 典型示例：用户已声明无 RAG 经验，后续优势分析仍写「RAG 丰富」。

   * 根因：否定性事实未入库或未注入；冲突更新失败。

   * 解决方案：memory_update 链路；来源+置信度；Gap/推荐强制 evidence。

4. Gap / 推荐缺依据

   * 典型示例：空对象推荐、或建议没有 why/sources。

   * 根因：输入材料为空仍强行生成；字段约束不足。

   * 解决方案：无材料时明确索取；Recommendation 结构校验；Evaluation 专项用例。

5. 材料解析失败 / 鲁棒性不足

   * 典型示例：只给岗位名+公司、或特殊中文 JD 格式时分析失败；面试结束复盘解析失败。

   * 根因：解析提示与兜底模板不完善。

   * 解决方案：质量报告标红跟踪；前端错误可读化；文档类型误传自动纠正（JD 实为简历则切换解析）。

### 11. 意图体系

1. 三层架构定义

   * **顶层：基础意图**（与代码一致）

     `memory_update` / `resume` / `jd_analysis` / `interview` / `career_consult` / `general_chat`

   * **中层：场景意图**

     * resume → 解析 / 诊断 / STAR / 按 JD 定制 / 自我介绍文案

     * jd_analysis → 职责拆解 / 匹配 / 公司研究（可推断须标注）

     * interview → 出题 / 文字模拟 / 语音模拟 / 复盘 / 技术追问

     * career_consult → 方向咨询 / 情绪陪伴 / Gap / 行动计划

     * memory_update → 补充、纠正、否定性事实

   * **底层：应答策略**

     路由到对应 Agent + 专属 Prompt +（重要输出）Evaluation + 更新 Memory/Task；建议带 sources。

2. 落地实现

   * LLM Few-shot/结构化 JSON 做主分类 + 关键词/规则兜底（如明确「优化简历」才打 resume）。

   * 特殊规则：焦虑/被拒 → `career_consult`；「问我一些技术问题」→ `interview`；补充经历类 → `memory_update` 优先。

   * 模糊输入（「我想转 AI 产品」）→ 澄清要 JD/目标，并触发 Gap + Next Action，而不是直接空谈适合与否。

3. 迭代优势

   * 新增能力（如 Recommendation、语音面试）挂到既有意图与侧栏，不堆工具墙。

   * Prompt 版本可管，评测集可回归。

### 12. 项目中遇到的最大的困难

**难点一：求职意图模糊导致 Agent 调度混乱**

1. 困难情景

   用户常说：「我想转 AI 产品，你帮我弄一下。」这句话可能同时像职业咨询、Gap、JD 分析、简历优化、面试。若直接乱路由，会出现：没简历却改简历、没 JD 却谈匹配、空聊适合与否。

2. 解决方案

   * 设计 **意图澄清 + 分步编排**：先要目标岗/JD 与简历材料，再进入分析与优化，最后面试。

   * Master 结合 **Task Memory**：识别长期目标后创建任务，侧栏展示当前进度与下一步；后续对话优先推进下一步，同时允许用户打断切意图。

   * 复合指令拆解为清单（先 JD，再简历，后面试），而不是一个 Agent 包办胡答。

3. 成效

   Master 质量套件路由相关用例通过（8/8）；产品从「功能菜单」变成「跟着任务走的求职伙伴」。

**难点二：简历优化与复盘中的幻觉（真实可投递底线）**

1. 困难情景

   生成模型天然倾向「写得更漂亮」。求职场景一旦虚构项目或指标，用户拿去面试会被打穿，产品价值变为负。

2. 解决方案

   * Evaluation Agent 横切：真实性 / 匹配度 / 风险分级。

   * high risk **阻断**可投递输出，返回问题列表与改写建议。

   * 精标集覆盖「提升 300%」「主导千万用户」等诱导；Dashboard 跟踪幻觉与 BadCase。

3. 成效

   Evaluation 套件能稳定打出虚构识别；Resume 防虚构用例可阻断。产品差异化从「写得顺」变成「经得起对照原文」。

**难点三（可选补充）：语音面试体验与链路延迟**

1. 困难情景

   真流式低延迟语音（WebSocket ASR）未做，当前是「说完 → 转写 → LLM → TTS」，易被感知为慢；且文本 LLM 与语音 API 必须配置分离。

2. 解决方案

   * 产品上做成电话式交互：自动开麦、停顿提交、可打断、固定展示面试官提问、大红结束键。

   * 工程上 ASR/TTS 与文本 Base 分离，避免误打到无音频能力的模型。

3. 成效

   闭环可演示；同时诚实保留「非真流式」为后续优化项——体现产品经理对体验与技术边界的判断。

***

### 附：需求优先级与交付矛盾（STAR，方法论来自智能客服项目）

**S**：质量套件暴露部分链路未达标（如个别 JD 解析失败、面试复盘解析偶发失败），但作品集演示节点临近，需要可讲清楚的稳定主路径。

**T**：在有限时间内保证「防幻觉底线 + 主闭环可演示」，并把已知缺陷变成有归因的 backlog，而不是装作没有。

**A**：

1. **底线兜底**：虚构类必须能拦截；材料缺失时索要信息，不硬生成履历。

2. **分阶段演示路径**：先跑通「上传简历 + JD 分析 + Gap + 简历优化（含阻断）」；语音面试与复盘作为增强项，已知问题当面可讲清。

3. **BadCase 日清**：质量报告未通过项逐条归到 Prompt / 解析 / Evaluation / 前端展示，进修复队列。

**R**：主叙事可稳定演示；未完成项有清单与复现路径，体现「用评测驱动产品」而不是「只调到自己觉得好」。

**【备注】什么叫「产品经理输入物」**  
不是让你去写后端代码，而是你交给研发 / 算法 / 自己验收用的**规格与约束**：问题定义、PRD、Agent 职责、意图规则、Prompt 产品要求、评测集、指标口径、验收清单、风险红线。有了这些，工程才知道「做成什么样算对」，面试官能听出你不是「调了两句 Prompt 的使用者」。

**【备注】AI 产品经理 vs 传统产品经理**  
传统 PM 更常交付页面流程与业务规则；AI PM 额外必须定义：**模型该做什么/不该做什么、上下文从哪来、幻觉如何拦、如何评测发版**。职小伴的差异化恰恰在 Multi-Agent + Memory + Evaluation，所以输入物重心在「智能规格」而不只在「按钮布局」。

## 1. AI 产品经理在本项目的职责边界

### 1.1 你应当负责（输入/验收）

1. **问题与定位**：求职场景痛点、差异化（相对 ChatGPT / 单点简历工具）。
2. **闭环与优先级**：先做什么、后做什么、什么叫 MVP。
3. **Agent 产品规格**：每个 Agent 的职责边界、协作约束、意图路由规则。
4. **Prompt 产品层要求**：角色、知识边界、输出格式、负面示例、拒答/阻断策略（可与工程一起落进 `prompt.md`）。
5. **Memory / Task 字段语义**：什么算事实、否定性约束如何处理、跨对话任务如何续写。
6. **质量体系**：Evaluation 风险分级、精标集场景、BadCase 归因口径、发版门槛。
7. **体验与验收**：Chat First、可解释建议、VERIFY 清单、演示脚本。
8. **风险红线**：虚构履历、无依据推荐、密钥与隐私不进仓库文档。

### 1.2 你通常不单独负责（但要懂、能验收）

- 具体框架代码、SQL 迁移、Docker/便携 Postgres 排障（可协作，见 [HANDOFF.md](./HANDOFF.md)）。
- 模型权重训练 / LoRA 训练流水线（本项目生产路径未做微调，见逐字稿 §8）。
- 真流式 WebSocket ASR 实现（HANDOFF 已列为已知限制）。

### 1.3 与工程的「接口物」一句话

你输出规格与评测 → 工程落在 `backend/app/agents/*/prompt.md`、API、表结构、Dashboard；你用 [VERIFY.md](./VERIFY.md) 与各 `*_QUALITY_REPORT.md` 做验收。

**面试一句话**：我不是调包调用大模型，而是把求职闭环拆成可路由的 Agent，并用 Evaluation 和精标集守住「真实可投递」底线。

## 3. 分项详写（1–17）

### 1. 问题定义与用户痛点文档 · 状态：部分具备

**目的**  
在写功能之前先定义「为谁解决什么问题」，避免做成又一个 ChatGPT 套壳。

**怎么做（AI PM）**  
1. 写清目标用户与场景（求职准备全流程）。  
2. 列出竞品/替代方案的结构性缺陷（不是功能多少对比）。  
3. 用可验证的表述定义痛点（无长期记忆、输出不可审计、链路割裂）。  
4. 明确非目标（例如：本阶段不做招聘方 ATS 对接）。

**【现状】项目里已有的内容**  
- [docs/prd.md](./prd.md) §1.2–1.6：工具割裂、缺少长期背景理解、心理压力；定位为 AI 求职伙伴。  
- [docs/product.md](./product.md)：相对「普通 AI 工具」的差异化表（无记忆 / 单模型 / 无审核 / 功能菜单）。  
- [docs/逐字稿-职小伴求职agent.md](./逐字稿-职小伴求职agent.md) §2：把模糊诉求「帮我找工作」拆成可落地闭环。

**【建议添加】独立《痛点与非目标一页纸》**（P1）  
- **补什么**：一页 Markdown：Top3 痛点、证据来源（访谈/自用/竞品）、明确 Non-Goals。  
- **原因**：`prd.md` 过长（万行级）且状态仍写「MVP设计阶段」，面试官很难在 30 秒内抓住痛点；作品集需要「一眼可读」的问题定义。痛点若不独立，后面所有 Agent 优先级容易漂成「什么都想做」。  
- **不补的风险**：被追问「你和 ChatGPT 差在哪」时只能背差异化口号，说不清问题从哪来。

**【备注】痛点 vs 需求**  
痛点是用户处境里的「疼」；需求是你提出的解决方案形态。先痛点后方案，避免一上来就写「我们要上 Multi-Agent」。

**【备注】Non-Goal（非目标）**  
明确本期不做的事，防止范围膨胀。例如职小伴当前不把「真流式低延迟语音」当已交付能力（见 HANDOFF 已知限制）。

**模板**

| 字段 | 填写说明 | 应基于现状填写 |
|------|----------|----------------|
| 用户 | 谁 | 求职中的转岗/社招等（prd 已列群体） |
| 场景 | 何时何地 | 准备材料→投递→面试训练 |
| 痛点 | 可验证 | 无记忆；易虚构；链路割裂 |
| 现状替代 | 用户现在怎么办 | ChatGPT / 单点简历工具 / 题库 App |
| 非目标 | 本期不做 | 真流式 ASR；重 RAG 文献库 等 |

**面试一句话**：我先定义的是「无记忆、不可审计、无闭环」，再决定上 Multi-Agent 和 Evaluation，而不是先堆功能。

### 2. 产品定位与差异化一页纸 · 状态：已有

**目的**  
让团队与面试官用同一句话理解产品是什么、不是什么。

**怎么做**  
写定位句 + 对比表 + 体验原则；每条原则能映射到一个实现约束。

**【现状】**  
[docs/product.md](./product.md) 已写：

- 定位句：理解职业背景、分析岗位、生成材料、模拟面试、持续提升的 AI 求职伙伴。  
- 差异化四维：Career Memory / Multi-Agent / Evaluation / Chat First。  
- 六条体验原则：Chat First、渐进采集、多窗口 Memory 共享、基于事实反馈、建议可解释、画像而非表单。  
- Phase 7/8 目标：从「问答」升级到「理解→发现问题→下一步」。

**【建议添加】**（P2，可选）  
在 `product.md` 顶部增加「一句话定位 + 三不」（不是 ChatGPT 包装站；不是功能菜单墙；不是可随意美化履历的工具）。  
**原因**：HANDOFF / `.cursorrules.md` 已有「不是什么」的工程约束，产品摘要页同步后，面试与开发口径更一致。

**【备注】Chat First**  
用户用自然语言表达需求，而不是先点「简历」「面试」等工具按钮墙。职小伴仍保留 JD/简历/语音入口，但是辅助，不是主导航墙（见 HANDOFF 输入区说明）。

**【备注】可解释建议（Explainability）**  
每条下一步要有「为什么」和依据来源（记忆 / 本次流程 / 外部检索）。这是 AI 产品信任设计，不是文案装饰。

**模板**

| 维度 | 普通工具 | 职小伴（摘自 product） |
|------|----------|------------------------|
| 用户理解 | 单次对话 | Career Memory |
| 任务处理 | 单模型 | Multi-Agent |
| 输出质量 | 无审核 | Evaluation |
| 交互 | 功能菜单 | Chat First |

**面试一句话**：定位不是生成器，而是带记忆与质检的求职伙伴。

### 3. 用户旅程与 MVP 闭环 · 状态：已有

**目的**  
把「求职」拆成可实现、可验收的阶段链路，避免无主线的功能堆砌。

**怎么做**  
画主路径；标每步由哪个 Agent/系统能力承接；定义最小可演示闭环。

**【现状】**  
- [docs/product.md](./product.md) MVP：

```
用户表达求职目标 → Memory → Job → Resume → Interview → Evaluation → 记忆更新
```

- [docs/HANDOFF.md](./HANDOFF.md)：对话 → JD 分析 / 简历优化 → 模拟面试（文字+语音）→ 复盘 / 画像 / 推荐。  
- [docs/architecture.md](./architecture.md)：请求经 Master 路由；面试状态机；重要输出经 Evaluation。  
- Phase 8：Career Gap、Task Memory、Recommendation、Next Action（product / architecture / HANDOFF 均有描述）。

**【建议添加】《主路径验收对照表》**（P1）  
- **补什么**：每一步对应 VERIFY 勾选项 + 质量报告相关项（例如 Resume 防虚构、Gap 有 evidence）。  
- **原因**：闭环在文档里「写全了」，但 [VERIFY.md](./VERIFY.md) §D 正式通过标准 = 脚本全绿 + **语音面试 5 项**，未把 Gap/Task/防幻觉列为硬门槛——旅程叙事与验收口径不一致，面试深挖「你怎么证明闭环可用」时会露怯。

**【备注】MVP（Minimum Viable Product）**  
最小可行产品：用最小功能集验证核心价值假设。职小伴的核心假设是「长期理解 + 专业分工 + 输出可审计」能优于单次 Chat。

**【备注】用户旅程（User Journey）**  
用户从认知到完成目标的阶段路径。AI 产品要标出每段「上下文从哪来、模型输入是什么」。

**模板**

| 步骤 | 用户动作 | 系统能力 | 现状证据 |
|------|----------|----------|----------|
| 表达目标 | 自然语言 | Master + Task | master prompt；HANDOFF Task |
| 分析岗位 | 上传/粘贴 JD | Job + Gap | job/career_gap prompt；VERIFY Gap |
| 优化简历 | 上传简历 | Resume + Eval | resume/evaluation prompt |
| 模拟面试 | 文字/语音 | Interview | voice panel；VERIFY 语音 |
| 下一步 | 查看建议 | Recommendation | recommendation prompt |

**面试一句话**：闭环不是页面列表，而是 Memory→JD→简历→面试→评价→再记忆的飞轮。

### 4. 需求优先级与范围裁剪原则 · 状态：部分具备

**目的**  
资源有限时决定先后；AI 项目尤需把「安全/真实性」放在体验彩蛋之前。

**怎么做**  
定原则（价值 × 风险 × 成本）；列 Must / Should / Could；用评测结果回流改优先级。

**【现状】**  
- 逐字稿明确口径：**先防幻觉底线 → 主闭环跑通 → Chat First 体验**。  
- 工程约束 [`.cursorrules.md`](../.cursorrules.md)：重要 AI 输出必须经 Evaluation；Agent 模块化。  
- 实现顺序从 README Phase 0–8 可见：先 Chat/Master/Memory，再到 Job/Resume/Interview/Eval，再到语音与 Gap/Task。  
- VERIFY 硬门槛却偏向语音体验项（见上）。

**【建议添加】《优先级原则 + Now/Next/Later》一页》**（P0）  
- **补什么**：  
  - P0：虚构拦截、Master 路由正确、简历/JD 主路径、Memory 关键写入（尤其否定性约束）。  
  - P1：Gap/Task 跨对话、Recommendation sources、面试复盘稳定性。  
  - P2：四季主题、真流式语音、重 RAG。  
- **原因**：  
  1. Memory 质量报告为 **0/7**（`MEMORY_AGENT_QUALITY_REPORT.md`），与「Memory 是核心差异化」冲突——说明优先级执行与叙事可能脱节，PM 必须用书面原则把「先修记忆验收」提为 P0。  
  2. 没有书面裁剪原则时，体验项（主题、布局）容易显得与质量项同等，面试官会问「你怎么取舍的」。  
  3. HANDOFF 已承认 Embedding 未强依赖——应写进 Later，避免被追问成「RAG 没做完的半成品」而非「有意阶段取舍」。

**【备注】RICE / 价值-风险矩阵（简释）**  
RICE：Reach（触达）× Impact（影响）× Confidence（信心）÷ Effort（工作量）。AI 场景建议把 **风险**（幻觉伤害）单独加权：高风险能力未达标时，不应用体验需求插队。

**模板**

| 层级 | 原则 | 职小伴对应现状 |
|------|------|----------------|
| P0 底线 | 不伤害用户求职诚信 | Evaluation high 阻断；Resume 禁虚构 |
| P1 闭环 | 主路径可演示 | JD/简历/面试 |
| P2 体验 | 好用爱用 | 三栏、主题、语音体验打磨 |
| Later | 明确推迟 | 真流式 ASR；强 RAG |

**面试一句话**：我的排序是防幻觉 → 闭环 → 体验；语音流式和重 RAG 是有意后置。

### 11. Evaluation 规则与风险分级 · 状态：已有

**目的**  
在用户看到「可投递结果」前增加质检闸门，守住真实性。

**怎么做**

**【现状】**

- 分档：表达润色/合理归纳/轻微结构化 → low；事实新增 → medium/high。  
- 简历：参与≠主导；禁增项目指标；注意误伤合理归纳。  
- 面试回答权重：理解 20% / 结构 20% / 专业 30% / 匹配 20% / 真实 10%。  
- Gap / Recommendation / 复盘均有检查重点。  
- 输出 JSON：`risk_level`、`score`、`problems`、`fabricated_claims` 等。  

质量：`EVALUATION_AGENT_QUALITY_REPORT.md` **6/7**，均分 4.43/5；存在「可信改写误伤」部分通过。  
产品：高风险可阻断（Resume 防虚构用例在 Resume 报告中体现）；Dashboard 看幻觉/BadCase（api.md / frontend dashboard）。

**【建议添加】《阻断策略产品说明》**（P1）  
- **补什么**：何种 risk 对用户显示什么（阻断全文 / 警告可编辑 / 仅记录）；误伤申诉/放行流程（作品集可简化为「降低阈值 + 加负面例」）。  
- **原因**：规则在 Eval prompt 很细，但**产品层阻断 UX**未单独成文；且 6/7 含误伤，说明阈值与产品文案需要 PM 定义「宁可严一点还是体验优先」的原则。

**【备注】Evaluation（评估/质检 Agent）**  
对其他 Agent 输出做审核的层。  
**【备注】风险分级**  
用 low/medium/high 决定是否展示、是否入库 BadCase。  
**【备注】忠实度（Faithfulness）**  
生成内容是否严格基于给定上下文，不编造。

**模板**

| 输出类型 | 必查项 | high 时产品行为 |
|----------|--------|-----------------|
| 简历优化 | 虚构项目/指标/职责升级 | 阻断可投递稿 |
| 面试复盘 | 虚构经历、分数脱离对话 | 不可展示虚假复盘 |

| 推荐 | 无 sources / 保证 offer | 不下发 |

**面试一句话**：Evaluation 是横切质检，风险分档写在 prompt 里，高风险不能当可投递结果交给用户。
